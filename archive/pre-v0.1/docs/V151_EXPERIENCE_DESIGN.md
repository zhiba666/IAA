# v1.5.1 前十分钟体验设计

日期：2026-09-10。状态：设计稿，可作为下一轮实施依据；本文提出的功能尚未实现，真人结果尚未采集。

基线：`14310d3`，正式玩法为 v1.5，软件版本 `2.0.0`，正式存档 schema 4。v1.5.1 是本轮产品设计名称。现有实现和验证见 [AUTOMATION_V15.md](AUTOMATION_V15.md) 与 [DEVELOPMENT_FOCUS.md](DEVELOPMENT_FOCUS.md)。

## 1. 本轮目标与交付边界

让首次接触游戏的人，在没有旁人指路的情况下，完成「第一笔销售 → 小幅设备改造 → 分段自动化 → 自动试运行 → 第一次扩建」，并理解自己的操作带来了什么变化。

每个关键状态都应回答三个问题：**现在发生了什么；我能做什么；做完有什么用。** 玩家可以自由选择购买顺序，引导应随实际状态接续。

本轮交付包括：统一目标与新手引导、搬运恢复提示、三类购买的收益说明、试运行与扩建诊断、准确的实测标签、轻量状态反馈、局部测试和本地试玩观察报告。复用首代图片，辅助高亮和进度使用 Canvas。

数值先沿用现状：装杯首级 30 金、A 段自动化 130 金、B 段 330 金、首次扩容 60 金、首扩 650 金与累计销售 1200 份、目标出货 3 份/秒、连续试运行 45 秒。前三项购买不是额外的顺序锁。暂停中的发布、真机安排仍按原计划处理。本轮不包含第二代素材、新经营系统、广告、离线奖励或批量重构。

以下来自代码阅读与已有截图，是待修正的界面问题或体验风险，尚不是新玩家反馈结论。

## 3. 前十分钟流程

时间区间沿用原方案的体验假设。进入下一阶段以真实状态为准，熟练玩家可以更快，游戏不为凑时长增加等待。

| 阶段与观察窗口 | 进入条件 | 玩家看到什么、做什么 | 退出依据 |
| --- | --- | --- | --- |
| 第一批原料，0–15 秒内 | 新厂 A 段尚未投送且未自动化 | 空仓时“爆锅正在生产，等第一批出料”；有货时高亮待装仓 | 可以预留正数货物 |
| A 段教学 | A 段有货且入口有余量 | “先点待装仓，再点装杯入口”；拖动同样有效 | 核心成功提交正数货物 |
| 等待装杯 | A 已投送、B 尚未投送，待发仓为空 | “装杯机正在加工，成品会进入待发仓” | 待发仓有可搬货物 |
| B 段教学 | B 有货且入口有余量 | “把成品送到出货入口，完成第一单” | 核心成功提交正数货物 |
| 等待首单 | 已送入出货入口、累计销售为 0 | “出货后获得金币”；短暂关注出货工位 | `totalSold > 0`，只由真实销售触发 |
| 理解设备，约 15–60 秒 | 首单完成，fresh 装杯仍为初级 | 目标“装杯能力 2→3 份/秒 · 30 金”；缺钱时提示搬可用货物 | 已购买首级装杯，或实际状态已进入更高优先级阶段 |
| 第一段自动化，约 1–2 分钟 | 首单已完成，有未接通的运输段 | 推荐 A：展示 130 金与差额，说明省去待装仓这一段搬运 | 该段真实购买成功 |
| 第二段自动化，约 3–5 分钟 | 已有一段自动化 | “这一段已自动；继续搬运另一段”；剩余段可购买时提示接通 | 两段都已接通 |
| 自动经营，约 3–6 分钟 | 双段自动，试运行未完成 | 按真实阻碍提示改造、等待稳定或观察合格进度 | 核心试运行完成 |
| 第一次扩建，约 6–10 分钟 | 试运行完成且仍在首代 | 显示已达条件及剩余销量、金币；达到条件后主动扩建 | 扩建命令成功，机器阶段增加 |
| 扩建交接 | 首次扩建成功 | “扩建完成，自动转运保留”；有真实仓容变化时标出增量，展示实际开放的下一项设备改造 | 反馈结束后接入已有经营目标 |

教学首批沿用“每段最多 4 份”，有多少就按规则搬多少，不强迫等满 4 份。之后使用当前整盘容量与真实入口余量。两段教学完成不等于第一笔销售完成。

### 路线适应规则

- 双段自动之后，目标优先进入试运行诊断。玩家没有购买装杯首级时，明确提示该设备目前只有 2 份/秒，须达到 3；允许当场打开装杯改造。
- 玩家先买 B，则跳过 B 的教学和购买提示，剩余 A 继续手动。玩家先扩容、先升爆锅或先自动化，保留其选择，按真实缺口续接。
- 教学推进过程中若发现生产恢复需要补 A，不能停留在“等待 B”无限等待；有实际缺料时给出上游补料动作。入口已满时不继续推荐向该入口搬货。
- 旧档、回访玩家、已自动化或已扩建工厂按真实状态直接接续。复用 `manualTransfers`、销售、等级、接通记录和里程碑判断，不增加一套强制教程进度存档。
- 达成某个教学步骤只降低提示强度，不剥夺自由操作。所有购买和扩建仍采用现有规则校验。

## 4. 统一目标与界面信息层次

首页使用三个清楚分工的信息区域：顶部显示金币和实测出货；产线显示货物、加工状态及有效入口；底部目标卡显示当前经营目标与主操作。

顶部提示、目标卡、场景高亮和主按钮共用一个派生目标。正常状态下，每处表达同一个方向，避免同时出现“改造装杯”和“攒自动化”两项竞争任务。

**经营目标与眼前动作分开表示。** 例如：目标标题为“装杯自动补料”；进度为“还差 47 金币”；操作提示为“待发仓有货，送到出货入口继续赚金币”。主按钮可显示“定位待发仓”，只定位和高亮，不代替玩家投送；满足购买条件时改为明确带价格的接通按钮。

| 状态 | 目标卡主操作 | 次要入口 |
| --- | --- | --- |
| 正在拿货 | 提示“送到装杯/出货入口”，使用现有目标区域提交 | 取消拿取仍可用 |
| 教学中有货可搬 | 定位对应源仓；从仓到入口仍由玩家操作 | 简短操作说明 |
| 改造推荐已可买 | “查看装杯改造 · 30 金”打开当前报价 | 自由查看其他工位 |
| 自动化已可买 | “接通装杯补料 · 130 金”或“接通出货补料 · 330 金” | 物流改造 |
| 资金不足、仍需手动 | 定位当前能继续出货的搬运段 | 查看购买详情 |
| 全自动且资金不足 | 显示真实生产与金币差额，允许观察 | 条件详情/设备详情 |
| 试运行受能力限制 | “查看装杯改造”等具体入口 | 试运行条件 |
| 等待稳定、合格计时中 | “查看试运行条件”，避免无意义的禁用扩建 | 物流/设备入口继续可用 |
| 扩建尚有条件缺口 | “查看扩建条件” | 需要改造时给对应工位入口 |
| 扩建条件全部满足 | “扩建 · 650 金币” | 扩建预览 |

已有设置、物流、工位选择都保留。打开面板时不强行切换工位；面板内保持报价与购买优先级。目标变化后不自动购买，也不让原按钮位置的一次重复点击购买下一档。

### 提示覆盖与恢复

呈现优先级为：当前弹层与持有货物的操作状态 → 最近一次错误的恢复提示 → 当前可执行动作 → 经营目标说明。购买成功可短暂反馈，结束后恢复派生目标。保存失败等真实错误使用已有错误区域，不被庆祝文案覆盖。

主线购买建议在金币足够时保持稳定，不因两仓库存逐帧变化反复切换。搬运提示只在当前建议已不可执行、存在确切下游缺料，或教学阶段变化时切换；短暂加工间隙可显示等待。试运行卡上重要原因立即刷新，进度数字按秒刷新。

## 5. 搬运、失败与帮助设计

点选和拖动共用核心预留/提交/取消；任何提示和特效都不能改变库存或额外增加金币。

| 触发情形 | 建议文案与行为 |
| --- | --- |
| 拿起一批 | “已拿 N 份，送到装杯/出货入口”；高亮唯一合法入口，影像避开手指 |
| 入口可接收部分 | “可放 N 份，余下留在原仓”；提交结果展示真实数量 |
| 空仓 | “待装仓暂无货，等爆锅出料”；若真正原因是上游缺料则引导补上游 |
| 入口已满 | “装杯入口已满，等机器处理”；有下游可搬成品时提示先处理下游 |
| 放错位置 | “送到高亮的装杯入口”；没有提交的货物仍在源仓 |
| 主动取消 | 安静恢复目标，不播放失败惩罚 |
| 双指、缩放、设置、切后台 | 释放预留，恢复时重新读取库存；不记为玩家误投 |
| 自动化之后继续手动 | 操作仍合法；试运行未完成时事先提示“手动补料后会重新观察自动运行” |

拟定辅助提示：新手阶段连续 6 秒没有有效进展，或 10 秒内两次相同无效操作时，增加一次对应入口的高亮和点按示意。触发阈值属于本轮候选，按试玩调整。只有存在可执行动作时才触发；正常等待加工、弹层、后台、持有货物和试运行期间不催促搬运。成功后退出增强提示，同类提示设置间隔，避免反复闪动。

基础可点击区域保持至少 44×44 逻辑像素。转运入口沿用较大命中区域，逐个验证 320×524 和 390×844 及安全区。重点是目标不被手指、面板或机器覆盖。

## 6. 三类购买的说明与接管反馈

| 购买 | 购买前核心说明 | 购买后核心反馈 |
| --- | --- | --- |
| 装杯首级，30 金 | “装杯处理能力 2→3 份/秒”；整线预测按现有规则显示 | “装杯改造完成”；后续新批次逐渐体现速度，已有批次照原规格完成 |
| A 自动化，130 金 | “待装仓会自动送入装杯口，省去这一段搬运” | A 路径短暂强调，再保留“已接通”；引导剩余 B 段 |
| B 自动化，330 金 | “待发仓会自动送入出货口” | B 接通；双段齐全后“整线已自动，可以开始观察试运行” |
| 首次物流，60 金 | “整盘、入口和仓位 24→36，减少补料频率” | 标出真实容量变化，保留玩家当前经营目标 |

命名统一使用“装杯自动补料”和“出货自动补料”，详情附 A/B 及起终点；不只写“自动补料”让人猜对象。

设备升级显示设备能力前后值；双段尚未自动时，在主说明中写“整线仍需手动送料”，自动运行预测为 0 的原因放到详情。双段已接通后，显示真实规则预测的整线变化；若某次改造不提高整线稳定出货，明确指出仍受哪个工位或运输限制。

物流保持可选项，不设为试运行或扩建的新增硬门槛。自动化的奖励是减少操作；设备是改变加工能力；容量是容纳更多货物。首单、升级与接管反馈可复用现有音效、文字和短暂高亮，关闭声音/振动设置继续有效。

## 7. 试运行状态与规则解释

保留现有认证规则：双段自动接通；两段接通与最近成功手动投送均已过去至少 10 个有效前台秒；加工和运输能力上限不低于 3 份/秒；近 10 秒真实出货不低于 3 份/秒；连续满足 45 秒。

**稳定等待的 10 秒与合格试运行的 45 秒分开显示。** 10 秒结束仅表示手动影响观察窗口已过去，若实际出货仍不足，不能承诺立刻开始或在某个固定时刻完成。

以下是解释优先级，实际是否计时必须共用核心判定，不由 UI 再判断一套条件。

| 状态 | 目标卡示例 | 具体动作/边界 |
| --- | --- | --- |
| 已完成 | “自动试运行已通过” | 永久保留，不因后续手动、缺料或扩建重做 |
| 自动化未接齐 | “还需接通出货自动补料” | 指向剩余连接 |
| 能力上限不足 | “装杯最多 2 份/秒，试运行需要至少 3” | 打开装杯报价；并列瓶颈或运输限制按真实配置解释 |
| 等待自动稳定 | “自动运行观察中，还需 7 秒” | 展示剩余窗口；若由成功手动投送触发，显示“手动补料后重新观察” |
| 近 10 秒实测不足 | “近10秒 2.7 / 目标3份每秒，等待出货稳定” | 展示实际供料/堵塞情况；可以查看诊断，不提供虚构倒计时 |
| 正在合格计时 | “连续达标 18 / 45 秒” | 展示实测/目标；提示无需继续搬运 |
| 曾有进度后被重置 | 一次性“刚才手动补料，试运行重新观察”或“出货未持续达标，重新计时” | 保留持久的当前原因；一次重置只提醒一次 |

当能力不足与窗口未结束同时存在，优先展示需要玩家行动的能力问题，在详情展示其余条件。单纯等待不能解决的配置，不提示“再等一会儿”。当前能力上限足够但短时实测偏低时，不立即劝买设备；先查看真实供料、库存与预测。

可计算的窗口：`remainingTicks = max(0, 各连接接通 tick + WINDOW − 当前 tick, 各连接最后成功手动投送 tick + WINDOW − 当前 tick)`，前提为已双段自动。显示秒数向上取整。未接通不是“还需 0 秒”。WINDOW 从规则读取，不在界面写死 10。

“能力上限”“预测稳定出货”“近10秒实测”保持语义区别。上限只用于核心必要条件；预测采用现有 `ProductionInsights`；实测来自真实出货历史。

### 前后台与持久进度

后台暂停，不按离开时间补产，也不让等待倒计时减少。仅取消/拿取不算成功手动投送，不应重置认证。读档使用核心保存的试运行进度与已完成证据，提示重新派生。一次性的重置说明放在界面会话中；不新增永久“失败次数”。

## 8. 实测标签和首次扩建

HUD 默认显示“实际出货 X 份/秒”。下方标签按优先级说明“开工不足10秒”“近10秒 · 含手动补料”或“近10秒实测”；配置刚变动可以附“更新中”。含手动标志以任一段最近成功手动投送是否落入当前观察窗口为准，不看功能是否启用。该标签表示窗口内有手动投送，不追踪每件售出货物的来源。

旧档与已完成试运行的工厂仍需准确标注最近实际操作。现有字段为 `insights.sampling.includesManualInput`，其计算把“仍有段未自动化”也算作含手动，需要改为当前窗口内确有成功手动投送。首页、设备详情统一消费修正后的字段；未自动化但窗口内未投送时只写“近10秒实测”，不能反向误标为“自动运行”。

首次扩建详情展示全部条件，不只给禁用按钮：

| 条件 | 显示方式 |
| --- | --- |
| 两段自动化 | 装杯补料已接通 / 出货补料已接通 |
| 自动试运行 | 未开始、当前原因、当前进度或已通过 |
| 产能里程碑 | 核心是否已记录目标 3 份/秒达标 |
| 累计真实销售 | 已售 N / 1200 份，显示剩余份数 |
| 当前金币 | N / 650，显示差额；是当前余额，不是累计收入 |

首页只突出一个当前阻碍，详情保留全部进度。`expansion.ready` 与 `expansion.reason` 是购买权限和阻碍顺序的权威来源；界面可提供恢复动作，但不能自行解锁扩建。试运行完成与产能里程碑写入之间可能存在采样间隙，只有当前无人窗口、能力和实测仍合格时才显示“正在记录达标结果”。若认证完成后又成功手动投送，或实测下降，里程碑可能等待更久：解释当前缺口，并继续保持“认证已通过”，不要求重做 45 秒。

试运行与产能里程碑一经记录永久保留；详情不能因当前瞬时速率下降取消勾选。后续扩建沿用各代目标和既有里程碑规则，不追加每代 45 秒认证。

购买前按 `bufferChanges` 显示实际仓容变化，按 `unlocks` 显示开放的改造；玩家若先买物流扩容，扩建未必增加当前有效仓容，此时不能写“仓位已扩大”。扩建后保留自动接通，提供“查看新改造”的入口。设备速度仍由对应改造决定，不用文字或动画暗示扩建已免费增加工作头或产量。表内首扩数值仅适用于 fresh；迁移旧档、后续代际均从当前 `view.expansion` 读取实际条件。

## 9. 小屏和表现规格

采用现有首代场景和目标卡区域，先做信息取舍。320×524 下首页目标卡维持约 100 逻辑像素级别的现有空间：标题、简短状态、主操作与详情入口；长原因在详情展示，关键动作和差额不能被省略号截掉。390×844 可增加一行当前阻碍说明，但不增加新的操作步骤。

搬运与弹层命中继续使用统一坐标；不通过扩大高亮图形覆盖真实不合法区域。目标切换时保持主按钮布局稳定；购买成功后先显示已完成状态，并按现有报价保护避免连点购入下一档。

当前状态不能仅靠颜色表达：自动段有“已接通”，有效入口有文字与边框，试运行有原因和进度。小屏优先保留目标、库存、售价和下一步，不同时展示三种速率概念。所有动效基于真实状态；不新增持续闪烁、强制庆祝弹层或免费奖励结算。

## 10. 数值校准方法

第一份试测构建保留所有上述价格、容量和门槛，先修复已确认的提示不一致、状态缺失与标签错误，避免一次同时修改玩法解释和经济参数。

现有三条脚本路线首段自动化为 1:22、2:12、2:26；双段接通为 3:08、4:01、4:14；首次扩建为 6:19、7:08、7:23。脚本预置首批投送并按固定间隔决策，这些仅是回归基线。

| 试玩发现 | 优先处理 | 参数调整条件 |
| --- | --- | --- |
| 找不到仓位、误把机器当目标 | 修改目标定位、文字和命中反馈 | 先不调价格 |
| 已能操作，但买不起时经常停住 | 给出当前有效搬运、解释赚钱路径 | 能独立操作后再判断价格 |
| 知道做什么，却觉得搬运重复且疲劳 | 查看平均实搬份数、频率、部分接收与仓满 | 在批量/容量或首次自动化成本中选择一组做候选 |
| 接通后仍反复手动搬同一段 | 加强接通反馈及剩余动作提示 | 先不为此调收入或奖励 |
| 双自动后进度为零，不知道升级装杯 | 修试运行原因和设备入口 | 先不降低认证标准 |
| 理解全部目标，等待金币阶段仍明显无聊 | 观察空等时长、可选升级带来的收益 | 单独评估首扩余额或销售门槛，保留自动能力认证 |

每次候选只调整一个因素组，配置集中在 `factory-rules.js`，保留基线与候选编号。批量、两入口和两仓属于同一容量组，联动调整，不只放大手持盘子。复跑积极、低频、非最优三路线，再用新的首次玩家观察。旧档成长定义和既有升级能力保持兼容，不统一涨跌所有代际价格。

## 11. 试玩数据与观察流程

首轮建议 5 名此前没有玩过本游戏的人，每人观察约 10 分钟。使用干净且独立的新档，告知“经营这家工厂，可以随时停止”，不提前讲搬运目标、购买顺序或解释试运行。先记录真实独立行为，必要帮助发生时记下时点，后续成绩明确标为有帮助。

桌面 Chrome 与手机触屏结果分别记录；鼠标仿真只能发现一部分问题。触屏等效点按必须实测。抖音真机另有平台验收，不能由浏览器试玩替代；恢复该验收前不把其通过列为本轮已完成结果。

### 最小事件与本地记录

复用 `first-sale`、`transfer`、`upgrade`、`automation`、`logistics-upgrade`、`automatic-trial`、`evolve` 事件，新增原因明确的无效操作、阶段变化和试运行开始/重置摘要。记录清单：

| 类别 | 必要字段或结果 |
| --- | --- |
| 会话 | 匿名测试编号、构建/规则版本、设备/视口、输入方式、是否新玩家、新档/续档 |
| 时间 | 首次有效投送、首单、首改、第一段自动、双段自动、试运行完成、首扩的有效前台时间 |
| 操作 | 两段手动次数、真实搬运份数、部分接收次数；无效投送按空仓/满入口/错目标分开 |
| 恢复 | 提示出现后是否完成有效动作；人工帮助时间、主动退出时间与阶段 |
| 试运行 | 首次开始、重置次数与原因、完成；用核心状态变化计一次，不每帧追加 |
| 理解 | 能否解释钱来自真实出货、自动化省去哪段、设备与仓位的区别、扩建还差什么 |
| 主观感受 | 哪一步最困惑、哪一步最重复、自动化后是否更轻松、是否想继续 |

成功手动提交才算一次有效搬运。双指、系统取消、切后台、打开设置与主动放回应分类，不混入误投率。自动运输计入生产统计，但不逐批写入观察明细。时间以核心 tick / HZ 为有效游玩时间，并额外记前后台与可见时长，避免把后台、页面节流或读取说明的差异藏起来。

当前 `platform.track` 只有最多 200 条内存记录，自动转运事件会挤掉早期里程碑。因此试测版需要一个独立本地摘要收集器：固定保留关键时间、累加计数，手动操作和重要状态变化保留有界明细；自动批次聚合。结束后通过 QA 入口导出 JSON/观察表。记录器失败不能影响游戏；不新增玩家端面板、不接入新分析服务、不改变已有上报开关。

观察者每位填写：完成/未完成阶段；首次卡住位置；帮助前的时间；两段实际搬运频率；是否重复操作已自动段；试运行卡住时采取的动作；扩建后是否知道设备仍需另买。访谈放在自由操作之后，避免问题本身提示答案。

### 进入下一阶段的标准

下表是本轮内部判定标准和候选体验目标，不是行业标准，也不是当前已测结果。

| 检查 | 标准 |
| --- | --- |
| 独立完成首单 | 首轮至少 4/5 能独立完成；记录首单时间，原方案 15 秒为优化目标，超过 30 秒逐人回看原因 |
| 理解自动化 | 至少 4/5 能指出接通后省去了哪段操作；仍未到达该阶段者单列，不能从分母中悄悄剔除 |
| 理解卡住原因 | 遇到试运行或扩建阻碍时，界面能帮助其说出原因与下一步；另用 QA 固定状态逐项验证 |
| 节奏 | 对照首段 1–2 分钟、双段 3–5 分钟、首扩 6–10 分钟；偏离时先定位操作、理解、选择还是价格原因 |
| 操作负担 | 汇报真实动作频率和平均搬运量，并结合主观疲劳；任何人因反复搬运或不明原因主动放弃都进入修正清单 |
| 扩建与接续 | 有人未在 10 分钟内到达就如实标记；必须有人完整验证扩建及下一步理解，不能拿脚本填真人空白 |

5 人样本用于发现问题，不用于推断留存或统计胜率。改动后优先另找 3–5 名新玩家复验；复用同一批熟练玩家只能验证操作回归，不能与其首次成绩直接比较。只要仍存在系统性误解，先修正并复验，再进入第二代美术。

## 12. 技术落地方案

### 统一数据流

`Game 真实状态与判定 → getView 诊断字段 → ProductionInsights 预测 → ExperienceDirector 目标 → HUD / 目标卡 / 高亮 / 主操作`

推荐新增小型只读 `src/experience-director.js`，统一生成 v1.5 的呈现目标。它接受视图、已有预测和必要界面上下文，不接收可变 `Game`，不写金币/库存，不启动第二套生产模拟。原 `_onboarding` 在 v1.5 呈现链路中不再与它竞争；baseline/P0 保留各自行为。

目标对象建议包含 `phase`、`goalId`、`title`、`statusText`、`actionHint`、`primaryAction`、`secondaryAction`、`highlight`、`reason`、`progress`。按钮动作是稳定类型加明确对象/报价，不能通过动态文案解析。

`Game` 提供可指定 `targetRate` 的共享自动运行条件 helper，始终返回双段连接、能力上限及限制项、窗口剩余 tick、近10秒实测与是否满足目标条件。试运行使用首次认证门槛；尚未达成的扩建产能里程碑使用当前下一代门槛。实际计时和 `getView` 共用这份判定，展示层只排序解释。认证的呈现层以已完成为最高优先级；底层 helper 不因认证已完成而早退，仍能解释后续更高产能目标。

临时目标、一次性成功/重置反馈和观察记录不写入生产存档。本轮以 schema 4 可兼容为目标，不因界面引导升级 schema。若未来确需持久新字段，另做明确迁移设计。

| 模块 | 具体工作 |
| --- | --- |
| `core.js` | 抽取共享试运行条件；暴露精确诊断；必要的试运行状态变化事件；保留现有核心规则 |
| `experience-director.js`（拟新增） | 阶段选择、自由购买路线、当下有效动作和目标说明 |
| `production-insights.js` | 复用已有预测及近期手动口径，输出限制解释；不按金币变化触发重新模拟 |
| `interface.js` | 统一首页引导、目标卡和速率标签；试运行/扩建条件详情；准确购买说明 |
| `main.js` | 主动作路由、报价保护、原因明确的取消/失败反馈、一次性状态反馈和本地 QA 记录 |
| `first-generation-scene.js` / `production-scene.js` / `art-layout.js` | 同一目标的源仓/入口/工位高亮；检查触控区域与小屏位置 |
| `factory-rules.js` | 首份试测保持基线；只有真人结果支持时提交独立数值候选 |
| `tools/` 与 `tests/` | QA 独立样例、观察报告输出、目标状态及交互回归 |

## 13. 开发顺序与验证

1. **冻结基线与确定状态契约。** 保存当前数值和三路线结果；定义目标对象、试运行原因及必要样例。
2. **完成核心解释和统一目标。** 优先覆盖空仓、首单未到账、缺钱、偏离购买顺序、双自动但装杯仍为 2 的状态。
3. **接入界面和交互。** 改目标卡、定位、详情、购买收益和实测标签；加入接管与扩建交接反馈。
4. **加入本地观察摘要并完成技术检查。** 只覆盖本轮新增行为与受影响规则，复跑现有核心、构建及布局回归。
5. **观察 5 名新玩家。** 输出有证据的卡点、时间、操作负担和修正清单。
6. **定向修正与复验。** 根据原因只调整相关界面或一组经济参数；分别报告技术通过和真人验证结果。

必须覆盖的行为场景：新开局两段投送到真实首单；源空/入口满/部分接收；先买 B、先买物流、先升爆锅；金币不足但可恢复生产；两段自动且装杯初级；刚接通、刚手动、实测不足、正常计时、重置和已完成；扩建多项条件缺口；认证刚完成但里程碑待下一秒记录；认证完成且里程碑未写入时再次手动；已认证但下一代产能不足；迁移旧档仍在首代时使用其真实扩建条件；高代接续；前后台/取消/写盘失败；两种视口和安全区。

关键断言：顶部/底部/高亮指向同一目标；推荐动作指向当前合法对象；查看详情不修改生产；旧批次与价格报价保持；试运行判定与旧规则在相同输入下逐 tick 一致；后台时间不减少窗口；已达里程碑不撤销；近期手动标签在边界正确切换；观察事件不会被自动批次挤掉或引发重复统计。

实施时执行 `npm test`、`npm run preflight`、`node tools/automation-balance.cjs`，并用 Chrome 检查本轮构建的真实布局与操作。模拟保持基线时结果应一致；改数值后报告候选与基线差异。抖音静态构建检查不计为抖音真机通过。

最终交付为：可运行的 v1.5.1 体验构建、对应测试结果、两种视口的关键状态证据、本地观察摘要、真人试玩记录，以及明确的“进入第二代美术 / 继续修正某项体验”的结论。当前本文仅完成设计。
