# 《小小爆米花厂》同类游戏爽点调研与当前缺口

**历史调研说明（2026-09-08）：** 本文记录移除完美判定前的规则、测量和建议。用户随后决定删除提前点火与完美判定，文中的技巧回报原型及压锅方向已撤回；模块、合同、批量出货和换代的分析保留为参考。当前规则见[移除完美判定](AUTO_BURST_SIMPLIFICATION_2026-09-08.md)，下文不是新的实现计划。

调研日期：2026-09-08。对象为当前工作区的合同与设备版本，包括最新六代产出形态。本文为设计评估与建议，未修改游戏规则。

**核心判断：当前已经具备生产、爆锅、交付、换代的反馈骨架，最需要补强的是“我的操作引发一次明显突破”的因果关系。** 完美操作的回报、模块组合的优势、财富集中释放的演出，以及换代后解决旧难题的体验，应当连成同一条循环。

依据包括当前源码、现有数值模拟的本次复跑、Chrome 本地隔离夹具的画面与精品合同交付检查，以及四款游戏的一手资料。竞品没有进行本次完整试玩；下文“爽点”是对已核实机制的设计分析。脚本会立即投资、接单和结算，模拟时间不代表真实玩家通关时间；浏览器夹具使用预置资源并明确推进了 60 秒 QA 时间，不读写正式存档，也不用于评判自然成长节奏。

选取三款移动端增量经营游戏作直接对标，另选一款桌面增量游戏观察实体反馈与组合设计。它们的体量和商业模式不同，参考具体机制，不照搬整套内容。

**当前已有的爽点，应继续保留**

当前不是空白点击器：散粒、满杯、双杯组、六杯整托、封装箱、整垛货已有不同生产动作；换代具有退场、安装、首批成品与真实收益倍率提示。普通爆锅、完美爆锅、蓄压释放已有标题、色彩或星芒差别。合同货款与零售现金分开结算，糖衣机确实影响加工，流水线也能接管活动合同的储压发运。

因此，“增加机器形态”“加上完美判定”“加入三选一合同”不能再算本轮新增建议。历史文档中的研发、工艺、旧档位、余热、并行委托和返场已退役，本次不以恢复这些系统作为默认方案。

**1. 第一优先：让完美操作真正值得追求**

当前 80 能量就能立即出整锅，92–98 为完美窗口，完美只多 20% 产量，点火后能量均归零。固定设备、无投料、持续循环且只比较爆锅产出时：

| 点火策略 | 每单位能量对应的爆锅产出 | 相对 80 提前点火 |
| --- | ---: | ---: |
| 80 点火 | 1 / 80 | 基准 |
| 92 完美 | 1.2 / 92 | +4.35% |
| 98 完美 | 1.2 / 98 | −2.04% |

这是产出/耗能的数学对照，未计普通自动收益，也不是人工操作收益实测。它说明当前“额外 20%”没有完整表达等待的成本。更直接的是：活动合同固定需要三锅，完美锅也只计一锅，追求最快交付会鼓励 80 提前点火。

规则证据：[点火与完美结算](C:/Users/chenweilun/Documents/GitHub/IAA/src/factory-rules.js:130)、[能量窗口](C:/Users/chenweilun/Documents/GitHub/IAA/src/core.js:6)。

建议先做一种清楚可见的技巧回报原型，例如完美产生可用于节庆合同的品质奖励，或触发短时间连爆。奖励同时体现在实际进度和画面上；“连续完美后的额外爆发”可作为后续候选。需比较整个 92–98 窗口与 80 提前点火，确保“完美”标签对应稳定优势。保留普通自动出锅，主动操作负责获得更好的结果。

**2. 第一优先：配装需要产生一眼能确认的优势**

当前两槽三模块确实存在取舍，但最接近“流派”的体验尚未形成。现有固定双缸机、Lv.12、第七单对照中，主动路线按允许次数投料并释放储压，没有额外使用火候点火：

| 配装 | 影院交付 | 精品交付 | 活动交付 |
| --- | ---: | ---: | ---: |
| 糖衣＋装箱 | 19 秒 | 33.75 秒 | 56.5 秒 |
| 蓄压＋糖衣 | 19.25 秒 | 33.75 秒 | 56.75 秒 |
| 蓄压＋装箱 | 19.25 秒 | 84.25 秒 | 56.75 秒 |

这组状态下，主动蓄压没有获得交付速度优势，缺糖衣则显著拖慢精品单。不同配置的零售现金与占用货款有差异，不能据此声称某组合在所有条件下都严格劣势。另一个限制是糖衣加工只按基础自动产量决定，爆锅不能直接加快这一工序。

证据：[既有固定经济对照](FACTORY_REDESIGN_2026-09-08.md)、[加工规则](C:/Users/chenweilun/Documents/GitHub/IAA/src/factory-rules.js:121)。

建议在现有三个模块内做出专长：装箱体现批量交付，糖衣体现高品质成品，蓄压体现抓住时机的大批爆发。至少让每个完整配装在一个明确场景下有可测优势；同时在主场景展示“卡在备货/加工/等出锅”的位置。不要靠增加模块数量掩盖现有组合差异偏小的问题。

**3. 第一优先：大收获需要更强的积累与释放过程**

现有爆锅固定喷发 18 粒，完美额外 8 个星芒；爆锅、储压和换代重点成品共用 2.6 秒展示。反馈不随这次收获相对平时的大小分档。订单交付共用 1.65 秒货车演出；合同类型虽被读入场景，但没有直接用于客户场景绘制。糖衣和装箱的模块效果仍会间接造成画面差异。

普通出货速度也较早饱和：`visibleRate = min(10, 2 × log2(1 + 每秒产量))` 在 31 份/秒封顶，之后还受成品离场间隔约束。同代只读场景模拟在固定升级、纯自动、无模块/爆锅事件下，第 3/4/6 代从 4 到 1000 份/秒均约 22 批/分钟。机械转速和包装细节仍会随升级改变，不能说画面完全不成长。

证据：[事件反馈](C:/Users/chenweilun/Documents/GitHub/IAA/src/production-scene.js:71)、[出货节拍](C:/Users/chenweilun/Documents/GitHub/IAA/src/production-scene.js:135)、[货车演出](C:/Users/chenweilun/Documents/GitHub/IAA/src/production-scene.js:406)、[爆锅提示](C:/Users/chenweilun/Documents/GitHub/IAA/src/renderer.js:28)。

缺的是“攒了一大批 → 一次放出来 → 看见收获落袋”的过程。建议做普通、满载、爆发三档反馈，以本次真实产出相对常态产出的比例驱动：储罐逐步充满、更多喷口同时工作、成品成列发运、客户车辆装满后离开。精品可强调糖衣包覆与礼盒成型，庆典可强调连锅发出。音效节奏和结算停顿同步区分等级。

继续保留粒子和实体数量上限，用批次组织、构图、节拍和镜头内的占用面积表达规模；性能限额本身不是问题。画面上的奖励等级必须与真实结算一致。

**4. 第二优先：换代后需要给玩家享受优势的机会**

第七到第二十单一直使用影院数量、精品加工、活动三锅三个模板。新合同数量按接单时的产能重新生成，奖金也会提高；接单后报价冻结，升级能帮助当前合同，这是已有优点。但下一单目标跟着能力扩大，玩家较少有机会直观看到“以前费劲的事，现在轻松完成”。

后续也有能力节点，如多头机批量升级、流水线活动自动释压，因此缺口是质变密度和兑现方式，不是完全没有自动化。[合同报价](C:/Users/chenweilun/Documents/GitHub/IAA/src/factory-rules.js:46)、[流水线接管](C:/Users/chenweilun/Documents/GitHub/IAA/src/factory-rules.js:184)。

建议在换代后设置一张规模固定的展示订单，让新机器快速处理旧难题，随后进入下一档合同。每代挑一个玩家能直接说出的新能力；优先扩展已有加工、储压和发运行为，不重新铺开多种货币与菜单。展示订单是候选设计，不能挤掉正常阶段的使用时间。

**5. 第二优先：中期操作要有更清楚的回报**

双缸机后每锅最多添料三次，每次只加 2 能量，主动添料对一锅蓄能最多贡献 6%。同一起点的既有中期策略比较中，自动糖衣＋装箱完成剩余十四单需 403 秒，主动蓄压＋糖衣需 380 秒，缩短约 5.7%。这里同时改变了配装与操作，不能把差值全算作点击收益；600 秒观察的操作次数还包含通关后行为，不能说“217 次操作只换 23 秒”。[当前添料规则](C:/Users/chenweilun/Documents/GitHub/IAA/src/factory-rules.js:165)、[中期模拟记录](FACTORY_REDESIGN_2026-09-08.md)。

建议把主动回报集中到少量有意义的时刻：一次操作解决当前瓶颈，或准确点火引发一次明显推进。前两项原型做好后再评估是否需要额外操作；单纯增加添料次数会增加操作负担，未必增强掌控感。

**6. 第二优先：终局需要明确选择完成感或下一轮追求**

本次复跑现有六条数值路线，其中主动零广告 525 秒、自动生产但持续投资结算 724 秒完成二十单与巨塔。两条路线的基础升级均满级，通关余额约为 4137.8 亿和 4077.4 亿；三个收藏共需 750 亿，开放时已经全部买得起。这证明该策略下收藏不足以支撑后续经营，并不意味着所有玩家都会在这个时间通关。

当时的复现入口为 `tests/balance.cjs` 的 `runAll()`；模拟策略与输出（当时路径：`tests/balance.cjs`，文件已删除）、[收藏价格](C:/Users/chenweilun/Documents/GitHub/IAA/src/factory-rules.js:242)。

如果本版定位为有限短篇经营，应将第二十单做成全厂联动、客户到场、成果陈列的终局高潮。若要承接多次回访，再设计有限的客户挑战或行为收藏，让完成条件要求不同玩法。单纯抬高收藏价格、恢复无限同类订单，只能增加等待，不能自动产生新爽点。

**广告的相关观察**

同一脚本中，高广告路线生产时间为 454 秒，但 19 次广告各按 30 秒计入后，总时间为 1024 秒，高于无广告的 525 秒。这不是随机实验，也不代表每个广告都不值得，但说明“数值奖励很大”不等于“现实推进更快”。后续广告奖励应承接一个玩家已经理解、明确期待的爆发或突破，并将广告耗时纳入比较。保留当前高广告强度的产品方向，不把本次研究解释成要求降低广告频次。

**建议先完成的一个原型**

先围绕现有庆典合同验证一条完整链：看见需要几锅 → 配好蓄压 → 准确点火获得明确额外收益 → 发出一批明显大于平时的货 → 奖励支持下一次设备突破。品质奖励、连爆和额外发运是待比较的候选，不应一口气全部叠加。

验证标准建议如下，属于本项目原型标准，不是行业基准：

| 要验证什么 | 怎样判断 |
| --- | --- |
| 完美值得 | 固定设备、升级、初始能量、合同与广告条件，分别比较自动、80 点火、92/95/98 完美；完美收益需覆盖等待成本，且对目标有明确帮助。 |
| 配装有专长 | 每个配装至少有一个优势场景；同时报告交付用时、最终现金与操作次数，避免把零售和合同货款重复计算。 |
| 爆发看得懂 | 隐去数字让试玩者辨认普通/完美/蓄压，并说明刚才为何变强；结合游戏实际结算核对。 |
| 换代有兑现 | 玩家能指出一项新增能力，并在实际操作中看到此前目标更易完成，而非只看到新模型与更大目标。 |
| 终局有意义 | 明确结束体验，或明确一个尚未被现有余额直接完成、且行为有变化的新目标。 |

先检验前三项，再增加内容长度。当前最有价值的投入，是让已有的点火、蓄压、加工和换代形成更强的操作回报与视听兑现。
